# 1C:Enterprise — EDT и Конфигуратор

## Описание

Работа в 1С:EDT (Enterprise Development Tools) и Конфигураторе: расширения конфигурации (CFE), обновление конфигурации, выгрузка/загрузка CF/CFE, командная разработка с Git-хранилищем, ролевая модель и best practices.

## Когда использовать

- Создание и управление расширениями конфигурации (CFE)
- Выгрузка конфигурации в файлы (CF) и обратная загрузка
- Настройка Git-хранилища для совместной работы
- Обновление конфигурации на новую версию платформы/БСП
- Просмотр и редактирование метаданных в EDT
- Работа с правами ролей
- Миграция с Конфигуратора на EDT

## Инструкции

### 1. Структура EDT-проекта

```
project/
├── src/
│   ├── cf/                          # Конфигурация (CF)
│   │   └── Configuration.xml
│   ├── cfe/                         # Расширения (CFE)
│   │   └── MyExtension/
│   │       └── Configuration.xml
│   ├── epf/                         # Внешние обработки (EPF)
│   │   └── MyProcessor/
│   │       └── MyProcessor.xml
│   └── erf/                         # Внешние отчёты (ERF)
│       └── MyReport/
│           └── MyReport.xml
├── .project                         # Метаданные EDT-проекта
├── .settings/                       # Настройки EDT
│   └── org.eclipse.jdt.core.prefs
├── build/                           # Артефакты сборки
│   ├── Configuration.cf
│   ├── MyExtension.cfe
│   └── commit.txt
└── packagedef                       # Зависимости (аналог package.json)
```

### 2. Расширение конфигурации (CFE)

```
# Создание расширения в EDT
1. File → New → 1C Project → Extension
2. Указать имя расширения (латиницей, без пробелов)
3. Выбрать родительскую конфигурацию

# Или через командную строку (EDT CLI):
edtcli create --project /path/to/project --name MyExtension --type extension
```

**Структура расширения:**

```
src/cfe/MyExtension/
├── Configuration.xml          # Метаданные расширения
├── Catalogs/                  # Добавленные/изменённые справочники
│   └── MyCatalog/
│       └── Catalog.xml
├── Documents/                 # Добавленные/изменённые документы
├── Roles/                     # Права ролей расширения
│   └── MyRole/
│       └── Role.xml
└── Subsystems/               # Подсистемы расширения
```

**Сборка CFE:**

```
# Через EDT (рекомендуется)
1. ПКМ на проекте → Build → Build Extension
2. Результат: build/MyExtension.cfe

# Через EDT CLI
edtcli build --project /path/to/project --output build/

# Через Конфигуратор (ручной способ)
1. Конфигуратор → Конфигурация → Выгрузить расширение
2. Сохранить .cfe файл
```

### 3. Выгрузка и загрузка CF/CFE

```
# === Выгрузка конфигурации в файлы (CF) ===

# Через EDT:
1. File → Export → 1C Configuration to Project Sources
2. Выбрать путь (src/cf/)
3. Выгрузка в XML-файлы метаданных

# Через CLI:
edtcli export --project /path/to/project --configuration

# === Загрузка из файлов в ИБ ===

# Через Конфигуратор:
1. Конфигурация → Загрузить конфигурацию из файлов
2. Указать путь к src/cf/
3. Подтвердить загрузку

# Через EDT CLI (только если EDT подключён к ИБ):
edtcli import --project /path/to/project --configuration

# === Выгрузка расширения (CFE) ===

# Через EDT:
1. ПКМ на расширении → Build → Build Extension
2. Или через командную строку:
edtcli build --project /path/to/project --extension MyExtension
```

### 4. Git-хранилище для командной разработки

```
# === Настройка Git-хранилища ===

# Инициализация репозитория
git init
git add .
git commit -m "Initial commit: EDT project structure"

# .gitignore для EDT-проекта
# build/
# *.log
# .settings/
# .metadata/
# bin/
# obj/

# === Ветвление для расширений ===

# Каждое расширение — отдельная ветка
git checkout -b extension/my-extension
# ... работа над расширением ...
git add .
git commit -m "feat: add MyExtension with catalog and document"
git push origin extension/my-extension

# === Merge request / Pull Request ===

# 1. Создать PR: extension/my-extension → main
# 2. Code review: проверить изменения в XML-файлах
# 3. Сборка: EDT собирает CF/CFE из ветки
# 4. Тестирование: загрузить в тестовую ИБ
# 5. Merge

# === Разрешение конфликтов в XML ===

# Конфликт в Configuration.xml (метаданные)
# Решение: EDT автоматически мержит, если конфликт не в корне
# При ручном мерже: сравнивать UUID объектов
```

**Правила Git для 1С-проектов:**

- **Один коммит = одно изменение** (один объект или логически связанная группа)
- **Коммитить** через EDT (Commit Changes), не через IDE
- **Не коммитить** build/, *.cfe, *.cf — они генерируются
- **Использовать** packagedef для зависимостей между расширениями
- **Ветка main** = стабильная версия, **ветки feature/** = разработка

### 5. Ролевая модель

```
// === Просмотр прав роли в XML ===

// Файл: Roles/MyRole/Role.xml
<Role xmlns="http://v8.1c.ru/8.3/roles"
      name="MyRole"
      uuid="...">
    <object name="Catalog.Номенклатура" read="true" insert="true" 
            update="false" delete="false" view="true"/>
    <object name="Document.РеализацияТоваровУслуг" read="true" 
            insert="true" update="true" delete="false" view="true"/>
    <object name="Catalog.Контрагенты" read="true" view="true"/>
    <object name="InformationRegister.ЦеныНоменклатуры" read="true" 
            view="true"/>
</Role>

// Права:
// read    — Просмотр (Чтение)
// insert  — Добавление
// update  — Изменение
// delete  — Пометка на удаление
// view    — Просмотр в списке

// === Иерархия ролей ===

// Роль-родитель (Базовые права)
//   └── Роль-ребёнок (Расширенные права)
//       └── Роль-внук (Полные права)

// В ней:
// Роль "БазовыеПрава" наследуется от role-родителя
// Роль "РасширенныеПрава" наследуется от "БазовыеПрава"
```

**Best practices для ролей:**

- Именование: `РольОбъект` + `_Чтение`, `_Запись`, `_Управление`
- Минимальные права: каждая роль — минимально необходимый набор
- Не дублировать: использовать наследование ролей
- Проверять: `ПроверкаПравДоступа()` в модулях объектов

### 6. Обновление конфигурации

```
# === Обновление на новую версию БСП ===

# Шаг 1: Обновить packagedef (если используется)
# Файл: packagedef
{
    "name": "MyConfiguration",
    "version": "1.2.0",
    "dependencies": [
        {
            "name": "БСП",
            "version": "3.1.9",
            "vendor": "1C"
        }
    ]
}

# Шаг 2: Загрузить новую версию БСП
edtcli update --project /path/to/project

# Шаг 3: Разрешить конфликты (если есть)
# EDT покажет конфликты в "Problems" view
# Разрешать через Compare → Merge в EDT

# Шаг 4: Проверить совместимость
1. Конфигурация → Проверка конфигурации
2. Исправить ошибки

# Шаг 5: Собрать и протестировать
edtcli build --project /path/to/project
```

### 7. Работа с Конфигуратором vs EDT

| Задача | Конфигуратор | EDT |
|--------|-------------|-----|
| Создание объектов | Визуально через дерево | XML-файлы |
| Написание модулей | Встроенный редактор | Внешний редактор |
| Отладка | Встроенная | VS Code + расширение |
| Версионирование | Git (после выгрузки) | Git (нatively) |
| Пакетная сборка | Скрипты на 1С | EDT CLI |
| Рефакторинг | Ручной | Автоматический |
| Поиск | Ограниченный | Полный текст |
| Работа в команде | Ограничена | Полная (Git) |

**Рекомендация:** для командной разработки — EDT; для единичных правок — Конфигуратор.

## Лучшие практики

- **EDT для команд** — Git-интеграция, code review, параллельная работа
- **Расширения вместо изменения БСП** — патчить, не менять исходники
- **Именование расширений** — латиница, PascalCase: `MyExtension`, не `МоёРасширение`
- **packagedef** — явное управление зависимостями между расширениями
- **commit.txt** — описывать каждую сборку (что изменено, почему)
- **Ветки feature/** — каждая фича в отдельной ветке, merge через PR
- **Не коммитить артефакты** — build/, *.cf, *.cfe в .gitignore
- **UUID в метаданных** — не менять вручную, пусть EDT генерирует
- **Роли — минимальные права** — не давать полный доступ без необходимости

## Антипаттерны

- ❌ **Работа в одном файле в команде** — Git-конфликты неизбежны
- ❌ **Изменение БСП напрямую** — обновление невозможно, используйте расширения
- ❌ **Ручное редактирование XML-файлов** — теряется контроль UUID, ломается структура
- ❌ **Хардкод UUID** — при клонировании/переносе UUID должны быть уникальны
- ❌ **Без .gitignore** — build/ и *.log засорят историю
- ❌ **Коммит без проверки** — всегда проверяйте через Конфигуратор/EDT перед push
- ❌ **Одно расширение на всё** — разделяйте по назначению (БСП, отчёты, интеграции)
- ❌ **ЗабытьRoles** — при добавлении нового объекта добавить права в роль
