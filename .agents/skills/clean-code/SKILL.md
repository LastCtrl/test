# Clean Code — правила качества кода

## Описание

Набор инженерных правил, по которым оценивается и улучшается код при написании, ревью и рефакторинге. Скилл задаёт единые критерии: границы ответственности, читаемость, обработка ошибок и типовые дефекты, которые должны блокировать приёмку.

## Когда использовать

- Ревью любого пул-реквеста или задачи (code-reviewer, code-reviewer-1, qa-engineer).
- Рефакторинг существующего кода (устранение дублей, длинных методов, god objects).
- Написание нового кода, когда нет спец-скилла под конкретный стек.
- Спор о стиле: скилл даёт общий аргумент вместо личного вкуса.

## Принципы

- **SRP (Single Responsibility)** — у модуля/класса одна причина изменения; смешение слоёв (HTTP + SQL + форматирование) — дефект.
- **OCP (Open/Closed)** — расширение через новые реализации/параметры, а не правка ветвлений в общем коде.
- **LSP (Liskov)** — наследник не усиливает пред-условия и не ослабляет пост-условия.
- **ISP (Interface Segregation)** — много узких интерфейсов лучше одного «на всё».
- **DIP (Dependency Inversion)** — зависимость от абстракции, а не от конкретного класса; внедрение через параметры.
- **DRY** — одно знание в одном месте; дубль логики устраняется, но преждевременная абстракция на 2 похожих местах — тоже вред.
- **KISS** — простейшее рабочее решение; сложность должна быть оправдана.
- **YAGNI** — не писать код «на будущее», пока нет требования.

## Читаемость и именование

- Имя описывает намерение: `daysUntilExpiry`, а не `d`, `tmp`, `data2`.
- Булевы — предикаты: `isActive`, `hasAccess`, `canRetry`.
- Функции — глагольные: `calculateTax`, `sendInvoice`; классы — существительные.
- Длина идентификатора пропорциональна области видимости: короткое имя допустимо только в узком цикле.
- Публичные имена не должны требовать чтения тела для понимания.
- Единый язык терминов: не смешивать `get/fetch/load/obtain` для одного действия.

## Размер и структура

- Функция делает одну вещь и находится на одном уровне абстракции.
- Ориентир: ≤ 20–30 строк и ≤ 3–4 параметра; превышение — сигнал к декомпозиции.
- Класс/модуль ≤ ~300 строк; несколько причин изменения — разделять.
- Вложенность ≤ 3 уровней: ранние `return`/guard clauses вместо `if`-пирамиды.
- Одна функция не смешивает вычисление, ввод-вывод и побочные эффекты.
- Побочные эффекты должны быть явны в имени или сигнатуре.

## Обработка ошибок

- Ошибки не глотать: пустой `catch {}` / игнор `err` — дефект.
- Отделять ожидаемый бизнес-случай (валидация, not found) от исключительной ситуации (сбой инфраструктуры).
- Падать рано на неверных входных данных, а не в середине длинной цепочки.
- Сообщение об ошибке содержит контекст: что делали, что пришло, что ожидалось. Без секретов и PII.
- Не использовать исключения как управляющий поток.
- Ресурсы освобождать детерминированно (`using`/`try-finally`/`defer`), не полагаться на GC.

## Комментарии vs самодокументируемый код

- Код — первичный источник правды; комментарий объясняет **почему**, а не **что**.
- Не дублировать код комментарием (`// i++`).
- Удалять закомментированный код — его место в истории git.
- Обязательные комментарии: неочевидные допущения, обход известного бага (с ссылкой), алгоритм с нетривиальной логикой, TODO с тикетом.
- Публичные API — краткая документация контракта (параметры, возврат, исключения).

## Типичные code smells и антипаттерны

- **Magic numbers/strings** — именованные константы вместо `3600`, `"active"`.
- **Long method** — метод на 200 строк с 5 уровнями вложенности.
- **God object** — класс, знающий половину системы.
- **Copy-paste** — скопированная логика, правки расходятся; выносить общее.
- **Флаговые параметры** — `render(flat: bool)` вместо двух осмысленных методов.
- **Глубокая вложенность** — `if/for/if/if`; early return упрощает.
- **Primitive obsession** — деньги/даты/ID как строки без инвариантов; нужен тип-обёртка.
- **Feature envy / middle man / dead code / shotgun surgery** — как признаки неверных границ.
- **Комментарий вместо рефакторинга** — когда сложность прячут словами.
- **Чрезмерная абстракция** — фабрика фабрик там, где нужен один вызов.

## Чек-лист ревьюера

- [ ] Имя и назначение каждого изменённого модуля понятны без вопросов автору.
- [ ] Нет дублей логики и magic-значений.
- [ ] Функции короткие, с одним уровнем абстракции, вложенность ≤ 3.
- [ ] Обработка ошибок полная; нет пустых catch и проглоченных ошибок.
- [ ] Побочные эффекты явны; ресурсы освобождаются.
- [ ] Тесты есть на новую логику и краевые случаи (пусто, ноль, максимум, ошибка).
- [ ] Нет закомментированного/мёртвого кода и отладочных принтов.
- [ ] Изменение локально: не тянет переписывание соседних модулей.
- [ ] Замечания сгруппированы: blocker / major / minor, без стилистических придирок вне согласованных правил.
